SnackBot Pi Link

How the navigation Raspberry Pi drives the robot through the Nucleo-F446RE motor controller: the three wires, every message in both directions, how the controller behaves, and where to tune it.

Wiring

The Nucleo runs from a 5 V, 1 A regulator fed by the robot battery instead of the laptop's USB. The Pi link is three wires: both boards use 3.3 V logic, so no level shifter, and TX crosses to RX. Every ground is common, and the Pi's 5 V is never connected to the Nucleo.

  1. Before the first power-up, check the regulator's output with a multimeter: it should read 4.75–5.25 V with no load.
  2. Power-up order: JP5 on E5V, battery and regulator on, check that the red LD3 power LED is lit, and only then plug in USB if you want to flash or read the log. Plugging USB in first can stop the ST-LINK from starting properly.
  3. The board's 5 V rail now comes from the regulator, so the encoders and the driver's 3.3 V logic supply are powered from it too. Together they draw well under the 1 A the regulator is rated for.
  4. To go back to USB power, move JP5 back to U5V.

  1. Encoder 2 was moved off D10 / CN7 pin 21 because the D10 header pin stopped passing its A signal. ENC2_ALT_PINS 1 in motor_pins.h selects the new pins; 0 goes back.
  2. CN7 pin 17 is the outer row, 9th pin from the USB end. The pin above it (15) is the debugger's SWCLK and the one below (19) is GND, so count carefully.
  3. Both encoders take 5 V (blue) and GND (green) from the board. Driving forward, both counters go up.
  4. To check an encoder, type telem,on on the USB port and turn the wheel slowly by hand: that wheel's speed in the T lines (vL or vR) should follow it, positive going forward. A speed stuck near 0 means one channel isn't arriving.

Pi link

On the Pi: enable the serial port and disable the Linux serial console (raspi-config → Interface Options → Serial Port), then open /dev/serial0.

Message format

One message per line in both directions: five comma-separated fields, then a newline. Empty bodies stay as empty fields. Type codes and keywords are matched without regard to case, and spaces around a field are ignored.

motor-instructiontype code ,turnbody 1 ,90body 2 ,body 3 ,body 4 \nend

Lines longer than 80 characters are dropped. Unknown types and bad values are ignored and logged on the controller's USB debug port.

Behaviour

During a turn

Every motor instruction except stop is ignored. The Pi should wait for turn-complete before sending the next one. stop brakes at once and still sends turn-complete with the angle reached.

Command watchdog

If no motor instruction arrives for 500 ms while driving straight or in reverse, the controller stops on its own. A crashed Pi can't leave the robot driving.

Odometer

Distance travelled by the centre of the robot, so forward and reverse both add to it and a spin in place adds almost nothing.

Startup

The controller checks the motor driver, then waits braked. LEDs start off. Nothing moves until the first motor instruction.

The Nucleo has one LED that firmware can control, so both LED messages share LD2 until real LEDs are wired.

Pi side in Python

import serial

link = serial.Serial("/dev/serial0", 9600, timeout=0.05)

def send(*fields):
    fields = (list(fields) + [""] * 5)[:5]
    link.write((",".join(str(f) for f in fields) + "\n").encode())

def read_messages():
    while link.in_waiting:
        line = link.readline().decode(errors="replace").strip()
        if line:
            yield line.split(",")

send("motor-instruction", "straight")
send("motor-instruction", "turn", 90)
for msg in read_messages():
    if msg[0] == "turn-complete":
        print("turned", float(msg[1]), "deg")

Tuning

Every value lives in Core/Inc/robot_config.h. Change it, rebuild, flash. Each wheel has its own speed PID with its own gains: duty = KP·err + KI·∫err + KD·d(err)/dt, nothing else. L = left wheel (M2), R = right wheel (M1).

Tuning order

Use tools/pid_tune.py (pip3 install pyserial matplotlib, then python3 tools/pid_tune.py, with no other serial monitor open). It plots each wheel's setpoint, speed and duty at 50 Hz, sends gains live with set,<name>,<value>, runs timed Forward / Reverse tests and prints rise time, overshoot, steady error and the duty each wheel needed. Live values last until reset: Print config gives the lines for robot_config.h.

  1. Wheels in the air. Set accel 100 so each run is a true step. Tune one wheel at a time: untick show L or show R to hide the other; each wheel's boxes only change that wheel.
  2. ki 0, kd 0. Raise kp (500, 1000, 2000, 4000…) until the speed starts to ring or the duty gets jagged, then halve it. With P alone the wheel settles below target; that's expected.
  3. Raise ki (start near 2×kp, then double) until the speed reaches the target within about half a second with no more than ~10 % overshoot. Too much ki shows as a slow wobble around the target.
  4. Leave kd at 0 unless the overshoot won't go away; the 100 ms speed measurement is too coarse for much D.
  5. Set accel back to 0.4, check Forward and Reverse, then repeat on the floor under the robot's weight and keep those gains. Print config gives the lines for robot_config.h.
  6. Drive 2 m straight. Each wheel is now controlled on its own, so the robot curves if one wheel runs slightly faster or is slightly bigger. Small curves are left to navigation.
  7. Command turn,360 and mark the start heading. Scale TRACK_WIDTH_M by actual turn ÷ 360 if it over- or undershoots.

Before the first drive

Checked on the chassis: M2 is the left wheel and M1 the right, and both drive forward on straight. A positive turn should spin the robot counter-clockwise seen from above (left wheel back, right wheel forward); if it ever turns the wrong way, swap LEFT_MOTOR and RIGHT_MOTOR.
  • PID gains are starting guesses, checked in simulation only. Expect to tune them.
  • Driver faults are logged on the USB debug port but don't stop the robot yet, and there's no fault message to the Pi.
  • ROBOT_MODE 1 in robot_config.h brings back the B1 bench demo.
Firmware: pi_link.c (UART and parsing), drive.c (PID, odometry, turns), robot_app.c (messages, button, LED), settings in robot_config.h. Branch two-motor.
